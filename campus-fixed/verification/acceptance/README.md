# t24：端到端验收 —— t18–t22 这一轮到底让学生多看到了什么

## 结论（先回答队长的问题）

**在现有的运营库（`data-operator` 的只读副本）上跑一次完整日常更新，学生可见事项新增 0 条**
（公开列表 100 → 100）；唯一被刷新的是 1 条既有事项的内容版本（5 → 6）。

**t21 救回的 6 条原生文章里，5 条不会出现在学生面前，1 条可见**——而且那 1 条
（辅修专业报名通知）在本轮之前就已经发布了。它们没有「卡在候选层」：
6 条都走到了人工/策略决策，5 条被明确 `reject`，理由是
「所有截止时间都已过去（对今天无事可办）」，事项随后被下架。

**在全新安装上**（契约命令的冷启动）公开列表 = **8 条**，也就是说产品「第一天能用」的样子是 8 条。

**所以这一轮对学生的直接收益是 0 条新增可见内容。** 收益在别处（见第 6 节）：
采集不再把整条文章判失败、退出码恢复报警意义、地址/附件缺口补齐、复核工作台可用。
这些都不该用「首页多了几条」来报告——这份验收就是为了不那样报告。

这是**系统**收益，不是**学生可见内容**收益——两者的差别就是本任务要钉住的东西。

## 3. 独立复现 t22 的退出码结论（不看它的测试文件）

我按自己的方式构造了三个场景，只看命令的退出码与打印的判据：

| 场景 | 构造方法 | 结果 |
| --- | --- | --- |
| **干净运行** | `data-operator` 副本 + `--apply --gateway-from-config`（首次） | **exit 0**；「来源 22 个：成功 11 · 降级 7 · 需授权 2 · 跳过 2 · **失败 0**」；两条中继 feed 打印为「跳过来源 …（feed_https_required）：通道没开，不是故障」 |
| **真实失败（我构造）** | 往副本里插入一个普通网站来源，host 取 `host-that-does-not-exist-t24.invalid`（只写副本） | **exit 1**；「失败来源 验收用坏来源（t24 构造…）：真实失败（**unsafe_address**）」；同一次运行里两条中继仍是「跳过」→ **跳过没有掩盖失败** |
| **真实失败（意外真实）** | 同一副本再跑一次 | **exit 1**；「失败来源 天津大学研究生院 · 学位通知：真实失败（**upstream_http_404**）」（同一栏目地址我随后直接探测是 HTTP 200） |
| 冷启动（契约命令） | `--data-dir .test-temp-acceptance --apply --gateway-from-config` | **exit 0**；「来源 20 个：成功 13 · 降级 5 · 需授权 2 · 跳过 0 · 失败 0」 |

判据与我看到的实现一致：**跳过 = 该来源的全部错误码都属于「可选通道未启用」家族**
（`feed_https_required` 等，抓取之前抛出）；**失败 = 源取不到 / 正文解析失败 / 抽取失败**。
t22 的结论独立复现成立。

顺带一个真实观察（不是缺陷、但会影响「干净运行」的可得性）：**连续快速重跑会让源级 404 抖动**——
第二次运行撞到「学位通知」源级 404，几分钟后同一栏目直接探测又是 200；
exit 1 因此是**正确**的（那一轮确实有一个源取不到），但每天连跑两次会看到不同的结果。

## 5. t22 提出的边界：全源都被设计内拒绝 → 仍退 0，当前发生了吗？

**没有发生。** 三次真实运行的成功来源数分别是 **11 / 13 / 14**（冷启动 13），
从来没有出现「0 个成功来源」的情形；同时每次运行都有新候选（14 / 16 / 109）。
证据是各次运行打印的「来源 N 个：成功 … · 降级 … · 需授权 … · 跳过 … · 失败 …」与
`verification/acceptance/compare_public.py` 的前后对照。

也就是说：这个盲点在当前数据上**不会触发**，但它仍然存在——
一旦某天所有来源都只被「设计内拒绝」挡住（0 个成功、无新快照），命令依旧退 0。
t22 已如实声明，本轮**没有修**，是否要单独报警留队长决定。

## 6. 那这一轮的收益到底是什么（如实说）

| 修复 | 对学生的直接可见收益 | 可验证的系统收益 |
| --- | --- | --- |
| t18（附件地址安全 / yzb 受信） | 0 条（当天的附件缺口不改变可见条数） | 智能与计算学部的 6 个附件能抓回、源不再整条 `unsafe_address` |
| t19/t21（原生文章不再被判 failed） | 0 条（那 6 条都因期限已过而不该发布） | 6 条 backlog `failed → completed`，不再每天重抓整篇；三个栏目不再整条失败 |
| t20（复核工作台） | 0 条（今天没有人过那 128 条） | 127 条队列可排序、可看依据、可带理由决策（工具就绪） |
| t22（退出码语义） | 0 条 | 干净运行 exit 0、真失败 exit 1（本次独立复现）；警铃恢复意义 |

**所以：本轮的价值是「让接下来每天的内容能正确地产出与报警」，不是「今天多了几条」。**
要让学生明天多看到东西，瓶颈在**人工复核 128 条**（t20 的工作台）与
**期限是否还在未来**（抽取规则：队列里有正文带日期串却没被认成期限的例子，见 t20 报告）。

**未验证 / 边界**

- 副本上的运行是**我的机器、我的网关配置**；公网/校园网直连环境未验。
- 「人工复核 128 条之后学生能多看到多少」**没有实测**：这需要人真的过一遍队列（本轮只验证工具有效，不验证产能）。
- 匿名视角只测了 `/api/v1/events`（API 口径），**没有用浏览器逐页渲染首页**（前端 SPA 未验）。
  移动端刻度见 t11/t15 的 `verification/mobile/`，与本轮不同环境。
- 「连续快速重跑会让源级 404 抖动」只观察到 1 次，没有做重复实验确认是站点限流还是偶发。
- 冷启动目录 `.test-temp-acceptance/`（167 个文件、真实抓取数据）留在仓库内供复核；
  它被 manifest 前缀规则排除，但**需要清理时请自行删除**。
- 本轮没有改任何产品代码（inScope 只有 `verification/acceptance/`）。
