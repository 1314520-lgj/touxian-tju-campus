# t25：复核队列按「标题 + 期限集合」分组（呈现层聚合，不丢候选）

## 结论（一句话）

复核工作台默认视图不再一行一条：**127 条待人工判断 → 94 组**（同一件事被多个来源/反复抓取
各存一份，合并掉 33 条重复行，人工要逐条决定的条目数 **-26%**）。
分组是**呈现层**的：候选、快照、审计一条不动（`--flat` 随时回到一行一条），
整组决策会先把组内候选 id 全部打印出来，仍然必须 `--reason`、仍然受 `--max-batch` 限制、
仍然要 `--yes` 才写入——五条守卫在副本上逐条实测过。

## 1. 分组规则与呈现

规则（`scripts/review_queue.py`）：

- `normalize_title()`：全半角归一（NFKC）+ 去掉首部序号（`1.` `（2）` `三、`）+ 去掉全部空白 + 去掉尾部标点；
  **故意不剥**栏目名/【转载】等前缀——只有标题真的只差这些的条目才会被并到一组；
- `deadline_key()`：候选已抽取的期限**时刻集合**（`at` 或 `date`，忽略精度/类型的写法差异）；
- `group_key()` = （归一化标题, 期限集合）→ 同一组 = 同一件事、同一套期限证据。

每组的呈现（默认视图）：**代表标题 · 来源数 · 期限 · 同组条数 · 同组其它候选 id · 快照合计 ·
机器为什么不决定（沿用 `classify()` 的原话）· 原文链接 · 下一步命令**。
`--limit` 现在限制的是**组数**，`--limit 0` 看全部；`--flat` 恢复原样；
`--show <组内任一 id>` 仍是单条详情。

## 4. 整组决策：先列 id，再确认（副本实测）

`verification/review/guard_walkthrough.py` 在 `data-operator` 副本上挑最大的一组（4 条）实跑：

| 场景 | 结果 |
|---|---|
| `--group <id> --accept --apply`（缺 `--reason`） | 退出码 2，「决策必须带 --reason」；数据未变 |
| `--group <id> --accept --reason … --apply`（缺 `--yes`） | 先打印 `整组将影响 4 条候选…：<4 个 id>` + 计划，退出码 2；数据未变 |
| 同一命令 + `--max-batch 1` | 退出码 2，「选中 4 条，超过 --max-batch 1…没有一步到底的批量入口」 |
| `--accept --reason … --yes --apply`（无条件批量目标） | 退出码 2，「--batch-filter 至少要给出一个条件，否则就是无差别批量」 |
| 合规整组写入（`--yes --apply`） | 退出码 0：4 条候选各写一条审计；**候选 323→323 · 快照 549→549 · 审计 973→977（+4）· 待判断 127→123（-4）** |

即：整组决策 = 逐条候选写入，分组没有把 4 条候选变成 1 条假候选，也没有出现「全部接受」入口。

## 5. 未验证 / 限制

1. **归一化只按「标题 + 期限集合」**：同一条通知在不同来源被改过标题（加/去栏目前缀、换措辞）
   时不会被并到一组——这是有意的保守选择，宁可少并也不把两件事合成一件。
2. 空白差异被完全忽略（`A B` 与 `AB` 视为同一个标题）；如果哪天出现「仅差空格但确实不同」的两条，
   它们会被并进一组——组内会打印「同组标题不完全一致」，决策前能看到。
3. 分组没有改动队列的**排序键**：代表项取组内分数最高的一条，组间仍按 T 层/分数/标题排序；
   因此「建议先看 34 组」与 flat 视图的「建议先看 46 条」不是同一口径。
4. 未在真实目录上执行任何写入（只读查询 + 副本演练）；本轮也没有改 `server/`、`config/`、`src/`，
   判定口径（`classify` / `Pipeline.review`）一行未动。
5. 没有跨天复测：127→94 是 2026-10-21 这一次队列状态下的数字，队列变化后组数会变
   （`dedup_check.py` 随时可重跑）。
