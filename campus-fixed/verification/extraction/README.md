# t23：「正文有期限线索、抽取却没产出 deadline」的成因与修复（campus-rules-1.12 → 1.13）

## 结论（一句话）

队列里 127 条 pending 候选**确实 0 条有未来期限**，但原因**不是**「正文里有大量没被识别的期限」：
逐条比对正文后，只有 **5 条**是「日期自带『前』、cue 表里没有这种写法」，
另外 1 条是既有 `于…前` 规则的字数上限卡住了带星期的写法（`(周五)16：00`）。
这两类都修了（红测先行 + 升版重抽）：**同样的输入，新规则比旧规则多认出 15 条候选的期限
（其中 1 条是未来期限），少认 0 条**。
更要紧的是诚实地说清楚：**公开事项数没有变化**（122 → 122），自动接受 17 条里只有 **1 条**
可归因于本次规则改动——t20 举例的那几篇（10月16日 / 4月10日 / 9月11日）在今天是**过去**的日期，
修好它们让历史数据正确、让今后同类写法可办，但不会让今天的队列变短。

## 1. 取样：队列 127 条里到底是什么情况

`verification/extraction/sample_missing_deadline.py`（只读打开 `data-operator`）逐条取候选正文
（`parsed.segments`），按句子找日期串，再判断 cue 类型：

| 类别 | 条数 | 含义 |
|---|---|---|
| B 只有「日期(+时刻)(之)前」写法 | **5** | 本轮要修的规律 |
| A 有期限 cue（`于…前`）却没抽出来 | **2**（同一篇的两个候选） | 既有规则的字数上限卡住 |
| C 正文有日期串但**没有任何 cue** | 50 | **必须继续保持不确定**（红线） |
| 正文没有日期串 | 50 | 纯栏目/流程/名单页，本来就没有期限 |

B 类的 5 条（原文逐字引文）：

1. «2027年春季学期交换生（第二批）项目通知» — 「**10月16日12:00前**，有意向申请本项目的同学请登录境外院校官网查询相关专业及课程信息…」
2. «2026年秋季学期交换生（第二批）项目通知» — 「**4月10日12:00前**，有意向申请本项目的同学请登录…」
3. «2027年春季学期交换生（第一批）项目通知» — 「**9月11日12:00前**，有意向申请本项目的同学请登录…」
4. «【转载】关于天津大学2025年拟录取硕士研究生调档函开放下载的通知» — 「…打印后交人事档案管理部门或学习工作单位，**8月31日之前**将人事档案原件寄送至我校」
5. «【学籍管理】关于对超过最长学习年限研究生进行学籍处理预警的通知» — 「**2026年6月30日前**未办理结业、肄业相关手续的，学校将依据《天津大学研究生学籍管理办法》作退学处理」

A 类：「请进入报账程序的项目**务必于2024年11月15日前**完成报账流程」等；
真正卡住的是同一批的「请各学院(部)**于2024年9月27日(周五)16：00前**，将已审核通过的选题申报材料…」
——`BEFORE_DATE_CUE` 原来只允许日期与「前」之间隔 8 个字符，`(周五)16：00` 是 9 个。

C 类样例（这些**不能**动）：「新华社北京10月2日电…」「发布日期：2025年11月14日」
「1月17日 14:00-16:30 工程数学基础」「关于8月25日至8月31日暂停预约驾车进校的温馨提示」。

## 2. 归纳出的两条规律（各有一个红测）

| 规律 | 红测（改前失败） | 改后 |
|---|---|---|
| 日期(+时刻)(±括号星期)**(之)前**，句子里没有任何 cue 词 | `test_clock_then_before_without_a_cue_word_is_the_deadline`、`test_date_then_zhizhiqian_is_the_deadline`、`test_date_then_before_in_a_consequence_sentence_is_the_deadline` | 认成 `school_deadline`（有时刻 → minute 精度，无时刻 → date 精度） |
| 既有 `于…前` 规则的字数上限太紧 | `test_weekday_parenthesis_and_full_width_clock_before_a_department_deadline` | `于2024年9月27日(周五)16：00前` → `college_deadline` @ 16:00 |
| **反向**：「前」在复合词里（前后/前期/前往）不是期限 | `test_a_date_followed_by_a_compound_word_is_not_a_deadline` | 「3月15日**前后**举行」→ **不再**产出期限（改前它会被当成校级截止——这正是红线被破坏的一例） |
| **反向**：裸日期串不是期限 | `test_a_date_mentioned_only_as_background_stays_uncertain` | 仍为**空**（与改前一致） |

## 3. 改了什么

`server/campus/content.py`：

- 新增 `TRAILING_BEFORE_CUE`：`日期(±时刻)(±括号)(之)前`，且「前」后不能跟 后/期/夕/往/来/者/年/天/日；
- 它同时进入 `DATE_CUE` 与 `DEADLINE_CUE`（进后者才会被判成期限而不是排期）；
- `BEFORE_DATE_CUE`：日期与「前」之间的字符上限 8 → 12，并补上 `(之)?`、加上同样的复合词排除；
- `EXTRACTOR_VERSION`：`campus-rules-1.12` → **`campus-rules-1.13`**（候选身份按 (输入, 版本) 取键，
  不升版重抽是空操作）；`test_extraction_accuracy.py::test_extractor_version_documents_the_current_rules`
  同步记录本轮规则变化。

## 4. 对照数字（真实数据副本上）

**同输入、新旧规则的逐条对照**（`attribute_rules_change.py`：旧规则副本 vs 重抽后副本，按快照集合配对 321 条）：

```
逐条对照: {'两边都没有': 303, '新认出期限（含过去）': 15, '本来就有（不变）': 17, '新认出未来期限': 1}
少认了期限（含过去）: 0      ← 没有回归
```

- 多认出期限：**15 条**（其中**未来**期限 1 条：«天津大学2026»，2026-11-19 / 2027-01-14 / 2027-06-10）；
- 少认：**0 条**。

**重抽 + 一次日常运行（`reextract` → `daily_update --apply`，同一副本）**：

| 指标 | 重抽前 | 重抽后 · 复核前 | 日常运行后 |
|---|---|---|---|
| 候选 | 323（pending 127 / rejected 173 / accepted 23） | 323+14（pending 315） | 337（pending **119** / rejected 193 / accepted 25） |
| 有未来期限的候选 | 17 | 18 | 19 |
| 复核决定 | — | — | **自动接受 17** · 拒绝 193 · 留给人 119 · 已合并 25 |
| 发布 | — | — | **13 条**（`planned_publish: 0`，发布错误 0） |
| 公开事项（active） | 122 | 122 | **122** |

**诚实结论**：自动接受 17 条里，**只有 1 条**（«天津大学2026»）是本次规则改动带来的；
其余 16 条本来就有未来期限，只是被重抽重新排进队列、再被同一套复核策略接受。
**公开事项数不变（122 → 122）**，13 条「发布」是同一批事项在版本升级后的重新发布——
所以本轮**没有**让公开列表变长，我也不会把它写成「多发布了通知」。

## 5. 红线：没有伪造期限

- 4 个反向用例（前后 / 前往 / 裸日期 / 发布日期）改后仍然**不产出期限**；
- 顺带修掉一个既有的**假期限**：「将于3月15日前后举行」过去会被报成校级截止；
- `precision` 语义未动：有明确时刻 → `minute`（`at`），只有日期 → `date`，没有 cue → 不产出；不确定的日期仍然不写成事实（队列里那 50 条 C 类保持 `没有可核对的截止时间…留给人判断`）；
- 没有为了让队列变短而放宽任何「无 cue 也算期限」的判定：新 cue 只认「日期自己在说『前』」这一种写法。

## 6. t20 的第二条观察：同标题重复（只给结论，未改 scripts/review_queue.py）

在 pending 队列上统计（`queue_numbers.py`）：**86 个不同标题 / 119 条 → 18 组重复、涉及 51 条（约 43%）**，
最多的一篇出现 **×4**（«湾创未来…首届粤港澳大湾区创业大赛正式启动»、«关于8月25日至8月31日暂停预约驾车进校的温馨提示»、
«关于企业入校招聘活动入校方式的通知»、«关于开展2025年“百校千企”线上人才对接活动…»）；
候选的 `snapshot_ids` 分布显示 11 条来自 2–5 个来源（同一条通知被多个栏目发布）。

结论：**值得去重**，而且成本很低——按「规范化标题 + 期限集合」分组即可把 51 条压成 18 条，
人工要看的条数从 119 降到约 86（-28%）。这不是抽取层的问题（每条候选背后是真实的不同快照），
所以本轮**没有**在 `content.py` 里合并它们，也没有改复核脚本（不在 in-scope）。

## 7. 未验证 / 限制

1. **没有跨天观察**：新规律在真实数据上只验证到今天这批候选；今后新通知的命中率要靠日常运行看。
2. t20 举例的 5 条都是**过去**的日期，所以它们在今天仍然不会变成「可办」——这是数据事实，不是修得不够。
3. 「自动接受 17 条 / 公开事项 122 不变」的口径基于 `daily_update` 的 JSON 摘要与事项 `status` 字段
   （`active` = 公开、`under_review` = 未发布）；`publication_audits` 里能看到最近的下架记录，
   但「13 条发布是否全部是重新发布」没有逐条核对事件 id（只核到公开总数不变）。
4. 复合词排除表（后/期/夕/往/来/者/年/天/日）是按语料归纳的白名单，遇到「10月16日前述材料」这种
   少见的「前+述」组合会继续命中；命中与否都会把原文引文一起写进 `raw_text`，可复核。
5. 本轮没有动 `events.py` 的复核策略、没有改 `scripts/`、没有写 `data-operator/`（mtime 未变）。
