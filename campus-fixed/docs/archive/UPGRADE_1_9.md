# 1.9 开发说明：任务1、任务2、任务3、任务4

已完成任务1—任务4；应用版本仍为1.8.0，公共API契约仍为1.5.0。

## 任务1：跨年日期

`content.date_values` 原先将无年份月日放入发布年份，超过183天便丢弃，导致12月底通知中的1月日期、1月通知中的12月日期变成未知。

现在依次尝试发布年份的上一年、当前年、下一年，跳过无效日期，按与发布日期的日历天距离选取最近日期；只有最近有效日期仍超过183天才返回未知。等距时保留尝试顺序中的首个值。原则与 `zh_time._resolve_month` 的最近月份匹配一致，但这里按具体日期计算距离。显式年份、区间终点继承、时间精度和证据原文处理保持原有规则。

回归覆盖2026-12-28→2027-01-05、2027-01-03→2026-12-30、同年10月12日，以及“12月30日至1月3日”的截止日和活动双端点。附加覆盖闰日、无发布时间、无效日期和183/184天边界。

先记录完整基线，再写失败用例，再修复代码；完整结果见 ACCEPTANCE.md。没有新增依赖，没有修改冻结契约、原始快照、样本数据库或前端产物。自动采集仍只产生待人工审核候选。


## 任务2：节假日、旬和学期相对时间

新增元旦（1月1日）、国庆节（10月1日）和上/中/下旬解析。明示年份和“今年/明年/去年/后年/前年”被实际消费；无年份的节日取距离通知上海本地发布日期最近的一次，月份限定词沿用最近月份规则。所有推导候选均带 `needs_review=true`，需要人工审核。

“前”保留日历边界，如“11月上旬前”为11月1日，不编造前一天23:59。旬本身是日期范围：上旬1—10日、中旬11—20日、下旬21日至月末。“十月中旬”不会伪装成10月15日：内部结果使用 `precision=period` 和起止日期；冻结Deadline契约无法表达范围，对外保留 `precision=unknown`，通过原有warnings字段提供范围及审核理由，未增加API字段或枚举。

寒假、暑假、学期末统一返回 `term_relative_requires_term_start`，无具体日期；即使没有发布时间也保留这一审核原因。无有效发布时间的节日/旬标记 `publication_anchor_required`。“元旦后三天内”等未支持的复合偏移标记 `calendar_relative_requires_review`，不按发布时间加天数。

流水线现在会在主提取器返回未知占位值、或同句已有另一日期时继续调用补充解析；补充结果的审核理由被保存。校验时以同一份原文证据重新计算，并要求匹配原文片段，不允许人工凭空指定日期。分钟精度补充结果按冻结契约只填写at、date为null；去重也按此格式比较。

提取器内部版本由 `campus-rules-1.2` 增至 `campus-rules-1.3`，使后续显式重新提取可识别规则更新；本轮没有重跑或改写随包真实样本。新增60个测试实例，覆盖八类短语全链路、跨年/时区/闰年、缺少基准、复合偏移、审核入库、证据原文及拒绝伪造日期。另修正1条旧测试对分钟精度date字段的不合法预期。完整测试数量与跳过原因见 ACCEPTANCE.md。

## 任务3：可读性重构（行为不变）

`content.py`、`delivery.py`、`events.py` 原本用紧凑写法（逗号后不加空格、赋值号两侧不留空格、多条语句用分号并排），可读性差。本轮先格式化这三个文件，再重构 `date_values`，两步各自独立成 commit。

两步都要求行为完全不变，因此给出的是**机器可验证的证据**，不是口头保证：

- **格式化**：对每个文件取 AST 摘要（`ast.dump`，排除行号/列号属性）。格式化前后摘要逐字节相同——只可能是版式变化。
- **重构**：`date_values` 从 230 行拆成 11 个小型命名函数，自身退化为编排入口，签名不变。把上一 commit 的旧实现取回，在**同一模块命名空间**内执行，对 **7,466 条真实文本 × 8 个锚点 = 59,728 次调用**逐条比对返回值，**0 处不一致**。

重构中有一处必须原样保留的细节：星期几「紧跟日期即视为该日期的标签」的判定会读取**已经累积**的候选列表。因此该扫描函数按原样就地追加，而不是先算好再合并——否则「周一周二」这类相邻写法会多出一次命中。同理，换行符按输入包原样保留（`events.py` 本就是 CRLF，`content.py`/`delivery.py` 是 LF）。

未新增依赖。ruff 只装进临时 venv 作一次性格式化工具，没有写进任何 requirements 文件。

## 任务4：依赖版本锁定

**核查结论：该要求已经在 1.8.0 基线上满足，本轮不需要改动任何文件。**

核查过程与依据：

- `deploy/` 下只有两处 Python 依赖安装，且都从 lock 文件安装：`deploy/campus/Dockerfile` 用 `requirements-campus.lock.txt`，`deploy/cloudrun/Dockerfile` 用 `requirements-cloud.lock.txt`（后者首行 `-r requirements-campus.lock.txt`）。前端为 `pnpm install --frozen-lockfile`。没有任何路径从 `requirements-campus.txt`（未钉版的范围依赖）安装。
- 把本轮工作副本的 4 个文件（两个 Dockerfile + 两个 lock 文件）与**未改动的 1.8.0 原始包**做 SHA-256 比对，四个文件**全部逐字节相同**。即「从 lock 安装」不是本轮补上的，1.8.0 就已经如此；`git log -- deploy/` 也显示这些文件只在基线导入 commit 中出现过。
- `python deploy/cloudrun/preflight.py` 六项检查全过（必需文件、基础镜像 `@sha256:` 摘要、云 lock 保留全部核心版本、两份忽略文件的密钥排除、健康接口契约），`ok: true`，exit 0。
- `requirements-campus.lock.txt` 为 **58 个钉版**、无嵌套 include、无非钉版行；`requirements-cloud.lock.txt` 为 **14 个钉版**并 include 核心 lock；合并后核心 **58/58 版本保留、无漂移**。
- 扫描 `server/` 下 **58 个 .py 文件**的全部 import，**没有任何第三方导入不在 lock 中**——说明 lock 既没有漏包，也没有多余。
- 在只含两个 lock 文件的目录（模拟容器 WORKDIR）执行 `pip install --dry-run --no-deps --ignore-installed -r requirements-cloud.lock.txt`，**72 个包（58 核心 + 14 云）全部解析出来**，证明核心 lock 通过嵌套 `-r` 被正确读到；另单独验证从其他目录用绝对路径指定时，pip 仍按**包含它的那个文件所在目录**解析嵌套 include，因此 WORKDIR 变化不会破坏安装。

因为本轮没有改动任何文件，也就**不存在放松任何现有锁定版本**的问题。详细证据见 `verification/task4/deploy-dependency-audit.log`。

未验证：本机没有 docker/podman，**无法实际构建镜像**；也没有真实云环境，未实机执行 Cloud Run/Cloud SQL/GCS 部署。因此「在容器内成功安装」是静态核查（安装命令 + 锁文件解析 + 预检脚本）而非实机构建验证。

## 任务8—10：后端审核与性能优化（2026-10-10）

本轮基于已完成前端产物的1.9输入包继续，三个改动分别提交。新增30个回归实例，完整后端测试从532通过增至562通过，8个PostgreSQL环境用例仍跳过，106个子测试通过。前端33项单元测试通过；冻结契约、前端源码与产物、部署锁版本、原始样本全部字节不变。

1. **人工审核关卡**：发现原实现会给清晰通知自动赋值accepted并向后台发出发布任务，与“采集只能产生待审候选”矛盾。现在统一生成pending；归并发布必须有同一候选修订的人工accept记录，遗留自动接受任务和错误/缺失审核记录都不能发布。内部提取器升至1.4，重新提取旧规则时回到审核；已有公开事项和不可变历史未改写。原有测试中自动接受的假设相应改成显式审核，证据校验保留。
2. **数据库读取并发**：独立get/list/revision/jobs/get_job使用读事务，避免SQLite查询占用写锁。嵌套写事务、CAS、队列领取、整体回滚和内存连接互斥保留。另一个写者占锁150ms时，合成读延迟中位数从180.063ms降至0.315ms。
3. **搜索一致性与性能**：FTS命中与版本凭据在同一快照内取得，消除并发刷新漏结果；当前索引确认无命中后直接跳过正文读取。过期索引、历史查询和ASCII任意子串保持全扫，评分和原文切片不变。73条公开事项的临时副本上，“奖学金”查询约3.57×，无命中约5.86×，五组响应完全一致；高频广泛命中只约1.12×，不宣称所有查询都同幅度加速。

验收和复现入口：ACCEPTANCE.md与verification/backend/。PostgreSQL、真实外部服务、镜像构建和生产压测仍未验证；不把本机计时当线上效果。全程没有新增依赖，也没有重新构建或改动前端。


## 任务11：独立复核与真实后端浏览器验收（2026-10-11）

上一轮的后端改动（审核关卡、读取并发、搜索收窄）由作者自己的测试证明，本轮改用独立证据复核，并补上此前一直标注"未验证"的真实后端浏览器端到端流程。**产品语义未变**，只修了 3 个可复现的缺陷并重建产物。

**独立复核。** 不依赖作者的合成夹具：把随包的 73 条公开事项数据库复制到临时目录，逐查询比较"索引收窄"与"全量扫描"两条路径——固定 11 个查询加上**每一个标题**里的汉字二元组，结果完全一致，并断言加速路径确实被走到（否则等价性会因收窄从未发生而空过）。同时验证了"当前凭据必有对应行"这一不变量、陈旧凭据会回退全量扫描、以及 1.3 提取器留下的 **outbox 行**（不只是队列任务）同样无法发布。新增 `test_search_narrowing_corpus.py`（17例）与 `test_review_gate_outbox.py`（3例）。

**性能复测。** 复跑作者的两个基准脚本：读取中位数 167.5ms → 0.432ms；`奖学金` 3.91×、无命中 4.91×、`GPA` 1.00×、`报名` 1.12×，5 组响应全部相等，SQL 语句数与公布值一致。数字在运行间波动范围内复现，结论不变。

**真实后端浏览器验收。** 9 个入口、84 项断言、74 张截图全部通过。每条入口都在自己新起的回环合成服务上运行——验证码有 30 秒冷却与每小时 6 次上限，共用一台服务会让后跑的入口收到 429 而不是被测产品。

**修复的 4 个缺陷。**

1. 移动端抽屉关闭后约 200ms 内仍可被 Tab 聚焦。`ui-review` 的键盘断言因此失败。该 CSS 与 1.8.0 逐字节相同，是**既有问题不是本轮回归**。修法：抽屉关闭且视口 ≤760px 时加 `inert`，立即退出 Tab 顺序，不依赖 `visibility` 过渡。
2. `a11y` 在入场动画结束前审计。`card-in` 动画 280ms，`stable()` 只等 2 帧（约32ms），axe 读到半透明文字的混合色并误报 12 处 serious 对比度违规；等动画结束后实测 0 处。修法：`stable()` 等待所有有限动画结束。
3. `ui-review` 关闭抽屉后 Shift+Tab 落到 skip-link，其聚焦态遮挡菜单按钮导致点击超时。这是第 1 条修复后暴露的正确行为，测试补上释放焦点。
4. 交付证据里带着作者机器的绝对路径。e2e 报告把刚写出的截图绝对路径直接推进 `report.screenshots`，`backend.xml` 的跳过原因与运行日志同样如此；1.8.0 手工清理过 6 个报告，但漏掉了 JSON 数组里被转义的那一批。修法：报告改经共享的 `relativeArtifact()` 写仓库相对路径；`tools/normalize_evidence_paths.py` 规范化既有证据（前缀取自运行环境，幂等）；`test_evidence_tree_hygiene.py` 三条用例钉住。

`dist/` 与 `web/` 已重建并逐字节一致，仅校园入口变化（+266 字节）。最终：后端 587 通过 / 8 跳过 / 0 失败 / 106 子测试（JUnit 701），前端单元 33 通过。证据在 `verification/audit/` 与 `verification/browser/`。

仍未验证：PostgreSQL、真实外部服务、镜像构建、生产压测。
