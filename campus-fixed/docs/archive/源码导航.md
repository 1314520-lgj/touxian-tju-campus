# 偷闲·天大版 — 完整源码包

把**天津大学公开通知**采集、抽取、复核、归并成「有依据的行动清单」的完整工程。
这份包是可运行、可测试的**源码全量**，不是构建产物快照。

- 后端 Python **8,415 行**（24 个顶层模块）+ 测试 **7,440 行**（36 个 `test_*.py` 文件）
- 前端 **1,249 行**（`src/campus/`：React 877 + 样式 372），另有测试 **2,145 行**（15 个入口）
- 契约：`domain-v1.schema.json`（90 KB，v1.5）+ `openapi.v1.json`（289 KB，**59 个操作** / 67 schema）
- 实测：**603 通过 / 8 跳过 / 106 子测试通过**（1.9 基线 587 + 自主维护第 1 轮新增 16 例）；前端单元 **33 通过**（见 [ACCEPTANCE.md](ACCEPTANCE.md)）

## 一、快速开始

### 跑后端（开发模式）

```sh
pip install -r requirements-campus.lock.txt
export CAMPUS_DATA_DIR=.campus-data        # 数据目录，默认就是这个
python -m server.campus_app serve --port 8765
```

Windows 上也可用 `start-campus.ps1`。

### 跑前端

```sh
npm install
npm run dev        # vite，5173 端口，/api 代理到 8765
npm run build      # 产出到 dist/（index.html=桌面版，campus.html=校园版）
```

### 跑测试

```sh
# 必须在工程根目录执行：测试用 server.campus.* 绝对导入
python -m pytest server/campus/tests -q
```

> **注意**：测试 import 的是 `server.campus.xxx`，所以工作目录必须是**工程根**。
> 进到 `server/` 里面跑会报 `ModuleNotFoundError: No module named 'server'`。

### 部署模式（`app.py`）

`app.py` 是**公开启动入口**（`python app.py`，也可作为 ASGI 应用 `app:app`）：

- **导入无副作用**：模块级只定义 `LazyApplication`，首次 ASGI 调用或 `main()` 才装配应用
- 装配前由 `bootstrap.prepare_runtime()` 校验数据目录可写、数据库完整、前端完整；任一不满足**明确失败**，
  不会自动复制一份临时数据库继续提供陈旧内容
- **不删 WAL/SHM**：交给 SQLite 自己恢复（`mode=rw`；明确拒绝 `immutable=1`，那会忽略仍在 WAL 里的已提交事务）
- **不轮换密钥**：`.server-secret` 以 `O_EXCL` + `fsync` + `os.link` 原子落盘，重启保持同一密钥
- 前端：完整 `dist/` 直接读取，不写盘；只有 `dist/` 不完整时才从完整 `web/` 原子复制
- 默认 `CAMPUS_PUBLIC_API_DOCS=false`，关掉 `/docs`、`/redoc`、`/openapi.json`
- 启动 20 秒后才开后台采集线程（先能服务、再开采集）

```sh
PORT=3000 python app.py
```

`web/` 与 `dist/` 是**同一份构建的两份拷贝**，服务两类打包行为：有的托管平台会剔除 `dist/`、保留 `web/`，
此时回退到 `web/`；而完整 `dist/` 可被直接读取，不要求启动时写盘。两者都保留是有意的，不是重复文件——
`ShippedFrontendParityTests` 会逐文件比对 SHA-256，只更新其中一份即失败。

## 三、核心架构：一条通知怎么变成一条公开事项

```
来源 (sources.py)
  │  15 个天大栏目，SafeFetcher 抓取：DNS 钉扎、TLS 主机名校验、逐跳 SSRF 检查、字节/超时上限
  ▼
文档 + 不可变快照 (snapshots)
  │  同一 URL 重发会产生新快照，旧快照永不改写
  ▼
解析 (parsed) → 抽取候选 (candidates)
  │  content.py：正文抽取（trafilatura，缺失时退化为按行提取）+ 日期/截止/材料/动作抽取
  ▼
运营复核 (ExtractionCandidate / ReviewDecision)
  │  分诊：接受 / 拒绝 / 取消；这一步是**人工**的，产品不自动公开
  ▼
归并事件 (events.py: reconcile_candidate → _strong_match)
  │  按事件身份规则把候选归到已有事件，或新建事件
  ▼
发布 (Events.publication → published / withdrawn)
  │  校验 EventPublicationPatch、检查 expected_event_version、递增版本、
  │  写 publication_audits、发出 public_event.changed
  ▼
公开 API / 前端
```

### 存储模型

**没有** 每实体一张表。是文档存储：`campus_records(collection, key, data, revision, updated_at)`，
`data` 是 JSON。主要 collection：

```
events(75)  event_versions(77)  event_snapshots(75)  event_receipts(75)
evidence(2531)  snapshots(345)  documents(345)  parsed(345)
candidates(163)  candidate_versions(266)  reviews(103)
publication_audits(2)  sources(15)  fetch_runs(78)  ...
```

查询时注意：**事件状态字段是 `publication_state`**（不是 `publication_status`），
值为 `published` / `withdrawn`。

### 确定性 ID（`uuid5(NAMESPACE_URL, ...)`）

| 实体 | 组成 |
|---|---|
| 文档 | `source_id + ':' + canonical_url` |
| 快照 | `document_id + ':' + digest + ':' + (parent_id or '')` |
| 候选 | `'candidate:' + sid` |
| 证据 | `f'{snapshot_id}:{segment_id}:{quote}'` |

幂等性依赖这些 ID：同样的输入必然得到同样的 ID，重复采集不会产生重复记录。

## 四、改代码前必读：关键不变量

1. **`campus-contracts/` 是冻结契约。** 改 API 形状必须同步改 schema 与 OpenAPI，否则契约测试会红。
2. **抽取与发布分离。** 后台采集**只**写待审核候选，绝不自动公开。这是产品设计，不是缺陷。
3. **原文快照不可变。** 新快照只能追加，不能改写历史；证据必须能回到原始快照。
4. **事件身份 = 一条通知，不是一个标题。**
   `_strong_match()` 用 `_document_roots()` 把附件快照沿 `parent_snapshot_id` 折叠回根文档：
   - 同一 URL 重发（根集合完全相等且唯一）→ 无条件合并
   - 不同来源文档撞标题 → 必须标题独立佐证才合并，否则置 `_pending_merge_review`，
     由 `reconcile_candidate()` 降级为 `under_review`
   - 该标志在每次 `_strong_match()` 入口复位，**不能跨候选泄漏**
5. **检索响应键是 `hits`**，不是 `items`；`items` 是 `/api/v1/events` 的键。
   命中里的 `excerpt` 是原文的**逐字切片**（注册成证据并按子串校验），前端只给它加背景色，
   不改字、不重排——高亮若改动一个字符，引用就无法核对。
   `index_status` 同时反映**本地** FTS5 索引是否落后，不再只在配了 Meilisearch 时才检查。
6. **中文索引是一元 + 二元切分**，不是 jieba。任何 Han 子串（长度 ≥2）都包含自身的二元组，
   所以二元索引保证可召回。改分词前先读 `zh_index.py` 顶部的注释。
7. **撤回是审计记录，不是删除。** 历史版本留在 `event_versions`，对外 `GET /events/{id}` 返回 404。
8. **投递的「接受」不等于「送达」。** 超时报 `unknown`，调用方不得盲目重发。
9. **相对时间不得静默锚定到发布时间。** `zh_time.py` 只在参照点确定时才给出日期：
   参照点是学期（`开学后`）或周次（`第8周`）时报 `unknown` 并进入复核队列，不猜。
   月份限定词必须被**消费**而不只是被匹配——只匹配不计算会返回格式合法、月份错误的日期，
   比不返回更危险。裸数字月份 + 日（`10月12日`）仍归主提取器，本模块不重复声明字面日期。
10. **全新数据库的并发首次启动必须能等待，不能直接失败。** 两个进程同时打开同一个**全新** WAL 数据库时，
   先到者切日志模式期间，后到者的 `BEGIN IMMEDIATE` 会拿到 `SQLITE_READONLY` 而非 `SQLITE_BUSY`，
   `busy_timeout` 不覆盖它。`Store._bootstrap()` 因此有界重试，并在两次尝试之间 `engine.dispose()`：
   输掉竞争的那条连接会终生只读，在原连接池上重试等于空转。**只重试瞬时竞争**，
   数据库损坏这类错误必须照常抛出。见 `db.py` 的 `_is_transient_contention()`。

## 五、建议的改进点（按性价比排序）

### 1. 中文日期/时间解析 —— 主要缺陷已在 1.8.0 修复，仍有边界

1.8.0 修复了三个**会产生错误结果**的问题（详见 [UPGRADE_1_8.md](UPGRADE_1_8.md)）：

- 月份限定词被吞掉：`12月底` 曾按发布月份算成 10 月，`十一月底`、`下个月初` 同样错，`下个月5号` 完全没有结果
- 学期相对时间被当成发布时间：`开学后两周内` 曾按发布日 +14 天给出一个具体日期，参照点根本不同
- 中文数字时刻丢失：`下午三点` 曾只得到日期、精度退化为 `date`

仍然**没有覆盖**的写法，会进入人工复核队列而不是被猜成具体日期：

- `本学期第8周` 只能报出周次，需要学期起点才能落成日期（`term_week_requires_term_start`）
- `待定`、`另行通知`、`以学校通知为准` 这类没有时间信息的表述
- `11.30 截止` 之类的紧凑写法与非标准分隔符

**方向**：接 [JioNLP](https://github.com/dongrixinyu/JioNLP)（MIT）做中文时间语义，
或继续扩 `zh_time.py` 的规则表并补边界用例。`date_patterns.py` 保持精简是有意的：
它只负责字面日期，相对时间由 `zh_time.py` 承担，两者靠 `supplement()` 的「不重复声明」约束协同——
裸数字月份 + 日（`10月12日`）归主提取器，本模块只处理限定月份（`下个月5号`）。

### 2. 正文抽取的鲁棒性

`content.py:132` 是 `trafilatura` 的 lazy import，缺失时 `warnings.append('trafilatura_unavailable')` 并退化为按行提取。
`requirements-campus.txt` 里已声明 `trafilatura>=2,<3`，但**没有固定版本、没有 lock**，
不同环境抽出的正文可能不一致。**方向**：固定版本并加正文质量回归测试（`test_body_quality.py` 已有骨架）。

### 3. 公众号来源（当前 3 个来源失败）

教务处三个栏目把通知发在微信公众号，`mp.weixin.qq.com` 对非浏览器访问返回「环境异常」验证页，
正文取不到。产品**正确地拒绝绕过**这层限制。**方向**：接已授权的 RSSHub / WeRSS feed，
走 `channels.py` / `ingestion.py` 已有的适配器接缝，而不是直接抓微信。

### 4. 前端 OCR

`localExtract.js` 目前是纯正则的浏览器本地抽取（设计上原文不出端，值得保留）。
若要做海报/图片通知识别，[RapidOCR](https://github.com/RapidAI/RapidOCR)（Apache-2.0）比 Tesseract 的中文效果好得多。

### 5. 检索质量

二元切分保证召回，排序用的是一段**可解释的小函数**（`search.py::_scan`）：

```
score = 段落重叠 + 标题重叠 × 10 − 同义词降权
```

「重叠」按命中的查询词长度累加（上限 10），所以长而具体的词压过短而常见的词；
`terms()` 已经把查询拆成自身及其二字组，因此字面重叠越长，贡献越多。
标题每个命中词固定加 10，因为标题就是事项自己的摘要。

**BM25 评估过，结论是这里不用。** FTS5 提供 `bm25(表, 各列权重)`，直觉做法是给标题高权重。
但事项标题被写进了该事项的**每一行**段落记录，于是标题命中会让该事项的所有段落都「命中」，
而 BM25 的长度归一化反过来偏爱**最短**的那一段。在真实通知上实测（标题
`关于2026年暑期社会实践活动的通知`，正文段落从「好的」到一整段要求）：
排第一的是「好的」，最后一名是真正写着要求的那段——甚至排在完全不含查询词的段落之后。
所以排序留在调用方：它能区分标题命中与正文命中，也让索引路径与全扫描路径共用同一个打分函数，
而不是把两种不同量纲的分数混在一起。这段推理记在 `zh_index.py` 的模块说明里。

**方向**：给「截止日期是否临近」「事项类型」加信号，但**必须保持可解释**——
排序依据要能和展示给用户的证据对得上，不要换成不可解释的打分。

**近义词命中的显示还差一步。** 字面命中过少时（少于 2 个不同事项），
`synonyms()` 会用策展近义词补召回（`SYNONYM_GROUPS`，例如 `('报名','申请','申报')`），
并靠 `penalty=1` 把这类命中排在字面命中之后。问题是界面上的标记只认**字面查询词**：
查询「奖学金申请材料」时，「【演示】校园竞赛报名」是由近义词「报名」命中的，
于是它**一条标记都没有**，读者看不出它为什么出现。要显示原因，需要接口把命中词返回，
而公共契约冻结在 1.5.0，本轮没有为这一个显示效果去动契约。见
[ACCEPTANCE.md](ACCEPTANCE.md) 的「已知限制」。

### 6. 事件归并可以更进一步

现在是「根文档 + 标题佐证」的规则法。跨来源同一事件（如教务处与学院同时转发）仍可能漏并。
**方向**：引入文本相似度（标题编辑距离 + 截止日期一致 + 正文重合度）做辅助打分，但**必须保持可解释**，
不要用黑盒模型直接决定是否合并——这会破坏现有的可审计性。

### 7. PDF 附件解析

目前用 `pypdf`（`requirements-campus.txt`）。扫描版 PDF 取不到文字。
**方向**：[Docling](https://github.com/docling-project/docling)（MIT）或接 OCR。
