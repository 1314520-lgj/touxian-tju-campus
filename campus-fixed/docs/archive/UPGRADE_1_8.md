# 偷闲·天大版 1.8.0 升级说明

产品版本 **1.8.0**，公共契约 **1.5.0**。本版在 1.7.0 可靠性强化版的基础上修复时间解析的正确性缺陷、恢复公开样本的复核决策链、清除交付物中的作者机器绝对路径，并把前端双副本的一致性变成可失败的检查。历史样本与线上状态分开说明；本轮没有部署历史链接、重新采集校园网站或真实外发提醒。

## 时间解析：月份限定词不再被吞掉

这是本版最重要的一处修复，因为它属于**看起来正确、实际错误**的一类输出。

原 `zh_time.py` 的 `MONTH_EDGE` 正则捕获了月份限定词（`本`/`下个`/`十一`/`12`），但在计算时**从未使用**它，一律按发布时间的月份求值。结果是：

| 通知原文 | 1.7.0 得到 | 正确值 |
|---|---|---|
| 请在12月底之前反馈 | **2026-10-31** | 2026-12-31 |
| 十一月底前提交材料 | **2026-10-31** | 2026-11-30 |
| 下个月初开始报名 | **2026-10-01** | 2026-11-01 |
| 下个月5号前报送 | 无结果 | 2026-11-05 |

返回一个格式合法、月份错误的日期，比不返回更危险：复核人员看到的是一个具体日期，只有一个通用的 `relative_time_requires_review` 提示。现在限定词会被真正消费：

- **纯月份数字**取**最近的**那一次出现，而不是一律往后推。10 月发布的通知说「12月底」是当年 12 月，说「1月底」是次年 1 月，说「9月底」是刚过去的 9 月，而不是 11 个月之后。
- **带年份**的写法（`2027年底`、`2027年3月底`）保留自己的年份。这里的 `年` 是可选的，否则 `2027年底` 的 `年` 会被年份组吃掉，回落到发布年份。
- **限定月份 + 日**（`下个月5号`、`下下个月3号`、`本月20日`）由新增的 `MONTH_DAY` 处理。
- **裸数字月份 + 日**（`10月12日`）仍留给主提取器，本模块不重复声明字面日期。

## 学期相对时间不再被当成发布时间

`开学后两周内提交` 原被 `DAYS_LATER` 匹配成「两周内」，静默按**发布时间**加 14 天，得到 2026-10-24。而「开学后」的参照点是学期开始，不是通知发布时间，两者相差数月。

现在检测到 `开学`/`新学期`/`入学`/`报到` 等学期锚点时，改为报告 `term_relative_requires_term_start`，不带日期，并把证据原文扩宽为「开学后两周内」，让复核人员看得到依据。这与既有的「第 8 周需要学期起点」处理保持一致：**不知道就不猜**。

另对按发布时间计数的 `days_after` / `business_days_approximated` 增加 `anchor: publication` 字段，把此前隐含的参照点写明。

## 中文数字时刻不再丢失

`请于下周三下午三点前提交` 原只解析出日期 2026-10-14，精度 `date`，时间被丢掉——因为主提取器的 `HOUR_PATTERN` 只认阿拉伯数字。现在 `下午三点`、`上午九点半` 与 `下午3点` 得到相同结果（15:00 / 09:30，精度 `minute`）。

`第三点` 是列举项不是时刻，因此加了 `(?<!第)` 负向后顾；`第一点、第二点、第三点说明` 不会产生时间。

## 公开样本保留复核决策链

1.7.0 的清理程序把 `reviews`(103)、`publication_audits`(2)、`fetch_runs`(78) 整表删除。隐私上可以理解，但代价是「**163 个候选 → 73 条公开**」这条漏斗在公开样本里再也无法核对——谁按什么理由判定，全部消失。

现在改为**保留决策、去掉人**：删除 `reviews.reviewer_id` 与 `publication_audits.actor_id`，其余字段（判定、理由、时间、候选 ID）原样保留，并在 `PUBLIC_SAMPLE.json` 中显式声明 `review_decision_chain_retained` 与 `redacted_actor_fields`。清理程序在写库前会断言每条记录都不超出允许的字段集合，且不含任何 actor 字段。

公开样本现在可以自行复核：**69 条 accept / 34 条 reject**，理由是「真实通知，进入公开流程」「栏目页而非通知正文」这类可读文本；2 条撤回审计说明了撤回理由。账号、会话、验证码、个人待办与偏好、日历令牌、任务/发件队列、幂等结果仍然全部排除。

## 交付物不再指向作者机器

原包多处把作者机器的绝对路径当成证据或后备：

- `verification/` 下 6 个报告共 **50 处**指向作者机器的绝对路径，另加 `backend.xml` 里 8 处 pytest 跳过原因；
- `manual-a11y-review.json` 的截图、样式表与 axe 报告三处；
- 8 个 e2e 入口把 Playwright 后备路径硬编码成作者机器上的绝对路径。

现在全部改为**相对交付根目录**的路径；e2e 入口改用共享解析器 `src/campus/tests/playwright.mjs`，依次尝试 `PLAYWRIGHT_MODULE`、常规 `playwright` 解析、当前工作目录下的 `node_modules/playwright`，失败时提示设置 `PLAYWRIGHT_MODULE`，而不是指向别人的磁盘。

`manual-a11y-review.json` 的截图在 1.8 轮重新采集，哈希随之更新；三项对比度测量（13.187:1、6.204:1、13.187:1）与前景/背景像素计数已在**新截图上逐项重数，数值完全一致**——渲染未变，只有 PNG 编码字节不同。

## 前端双副本不再可能静默漂移

`dist/` 与 `web/` 是同一份构建的两份拷贝，服务于两类打包行为：**有的托管平台会剔除 `dist/`、保留 `web/`**，此时启动回退到 `web/` 并原子复制；而完整 `dist/` 可被直接读取，不要求启动时写入。两者都保留是有意的冗余，不是重复文件。

真正的风险是**只更新其中一份**：那样在剔除 `dist/` 的平台上会静默提供陈旧前端。新增 `ShippedFrontendParityTests` 逐文件比对两份拷贝的 SHA-256，一旦分叉即失败（已实测注入差异会被捕获）。

## 发行清单可重建、可反向校验

1.7.0 的 `RELEASE_MANIFEST.json` 由包外过程生成，包内没有任何东西能重算或核对它——验收记录里「逐项核对文件哈希与 ZIP CRC」这句话当时无法被第三方复现。本版补上 `tools/build_release_manifest.py`：

- **生成**：`python tools/build_release_manifest.py --root .`，按路径分段、忽略大小写排序，输出 **593** 个文件的大小与 SHA-256，同一棵树重复运行得到相同字节。
- **拒绝**：生成时若发现 `.server-secret` 或 SQLite `-wal`/`-shm`，直接报错退出，而不是把它们哈希进清单。运行密钥和未检查点的日志不属于交付物。
- **反向校验**：`--verify <zip>` 对最终 ZIP 逐条比对解压字节的 SHA-256、长度与 ZIP 目录项 CRC，并报出缺失与多余条目。

清单头部同时记录派生来源 `derived_from_version` 与 `derived_from_manifest_sha256`。1.7.0 只有一个 `input_archive_sha256`，对 1.8 这种「从上一个发行目录派生」的包无法说明来源；基线目录即使删除，用清单哈希仍能对上。

应用自身的 `version` 也从 `1.7.0` 改为 `1.8.0`，与清单和验收记录一致；公共契约仍是 1.5.0，`openapi.v1.json` 的 59 个操作未变。

## 检索：状态如实上报，命中可以自查

三处改动指向同一件事——**让读者能自己核对，而不是相信一个结论**。

**本地索引落后时如实上报。** `index_status` 原本只在配了 Meilisearch 时才检查远端回执；
而随包默认没有 Meilisearch，本地 FTS5 才是唯一在用的索引，于是这个字段在本地部署里**永远**是
`current`，界面上的「索引更新中」永远不会出现。现在本地回执同样纳入检查：只要有一个已发布事项的
索引版本与正在服务的版本不一致，就报 `lagging`。答案本身不受影响——回执过期的会被整段扫描，
索引只能缩小工作量、不能删掉命中；这一条只是把「慢」如实说出来。

**检索命中标出查询落在哪里。** 结果原本只有标题和一段摘录，读者看不出**为什么**它排在这里。
新增 `src/campus/highlight.js`，给摘录里来自查询的字符加背景色。两条约束：
摘录是注册过的证据、按子串校验，所以标记后的字符必须**逐字拼回原文**（有单测钉住这条不变量）；
中文没有词边界、服务端按子串匹配，所以「两个字符以上且出现在查询里」就标记——
输入「奖学金申请材料」时，段落里的「奖学金」「材料」都会亮起来。标记只改背景色、不加内边距，
**不可能改变折行**；在 `--mark` 上的对比度是标题 10.3:1、摘录 5.0:1，都在 WCAG AA 之上。

**摘录不再切在句子中间。** 原来的窗口是 `原文[命中-60 : 命中+440]`，会在任意位置截断，
读起来像通知到这里就结束了。现在起点对齐上一个句读之后，终点在 80 字预算内对齐下一个句读，
或者把不足 80 字的尾巴整个收进来。切片仍然是逐字的，证据校验不受影响。

**字体栈补齐了 CJK 兜底。** 原来只有 `Microsoft YaHei` 和 Google Fonts 名 `Noto Sans SC`，
而 Linux 上装的通常叫 `Noto Sans CJK SC` / `Source Han Sans SC`——缺了就会退到没有汉字覆盖的字体。
现在按「拉丁在前、中文兜底」补齐 macOS、Windows 与 Linux 三类。Windows 上解析结果不变。

排序本身**没有**换成 BM25，尽管 `zh_index.py` 的说明一度这么写。见
[源码导航.md](源码导航.md) 改进点 5：标题被写进了每一行段落记录，BM25 的长度归一化会偏爱最短的那段，
实测把真正写着要求的那一段排到最后。说明已改成实际行为，并把这个反例记进了模块注释。

## 并发首次启动：追一条偶发用例，追出一个真缺陷

验收跑全量后端时，`test_parallel_development_cores_share_atomic_secret` 偶发失败。第一反应是「Windows 文件锁的抖动」，但单测隔离重跑 15 次仍失败 1 次，不是噪声。于是把它当缺陷查。

**根因**：两个进程（或两个开发核心）同时打开同一个**全新**的 WAL 数据库时，先到者执行
`PRAGMA journal_mode=WAL`（需要排他锁），后到者在此期间发出的 `BEGIN IMMEDIATE` 会得到
**`SQLITE_READONLY`**，而不是 `SQLITE_BUSY`。`busy_timeout` 只处理后者，所以后到者**直接启动失败**。
`db.py` 里原本已经为同一类竞态给 `journal_mode` 那一步加了重试，注释也写明了「journal_mode 不遵守 busy_timeout」——
但紧随其后的建表事务没有同样的保护，于是从这条缝里漏了出去。

**修复前的测量**（两次独立运行）：**6/200** 与 **7/120** 次失败，报错全部是
`attempt to write a readonly database`，位置是 `db.py` 的 `BEGIN IMMEDIATE`。

**修法**：把建表抽成 `Store._bootstrap()`，对这类瞬时竞争做有界重试（60 × 50ms）。
关键的一点是**两次尝试之间要 `engine.dispose()`**：输掉竞争的那条连接会**终生保持只读**，
在原连接池上重试只是空转——这一点是实测出来的，只加重试不换连接时失败率不降、还白等 3 秒。
重试**只认** `locked` / `readonly` 两个标记；数据库损坏、路径错误这类必须照常响亮失败，
新增的 `test_bootstrap_does_not_retry_a_real_failure` 就钉住这条。

**修复后的测量**：**120/120** 与 **180/180**，合计 **300/300** 全部收敛。
把 `BOOTSTRAP_ATTEMPTS` 临时改回 1 可稳定复现原报错，说明回归用例确实能捕获它，而不是只在旁边站着。

这件事对部署也有意义：`app.py` 支持多进程启动，同一个新数据目录被多个 worker 同时打开是真实场景，
原来会让其中一个直接起不来。

## 检索标记：核对到像素，也说清楚它做不到什么

标记功能本身在上一节已经说明。这里补的是**怎么证明它没有把事情弄坏**。

新增 `src/campus/tests/highlight-contrast.e2e.mjs`，对真实服务端命中做四项核对：

1. **标记前后逐字相同**：把渲染后的标题与摘录和接口返回的原值做全等比较。
   摘录是注册过、按子串校验的证据，高亮只要改动一个字符，引用就无法核对——这条是全等的，不是「看起来差不多」。
2. **每个标记都来自查询词**：相邻命中会被合并成一个 `<mark>`（`奖学金` + `材料` → `奖学金材料`），
   所以判据不是「标记文本是查询的子串」，而是「标记文本能拆成若干个查询子串」，用一个小 DP 判定。
3. **对比度从浏览器实算**：取计算样式，沿祖先链合成 alpha 得到真实背景，再算 WCAG 比值。
   实测 **标题 10.33:1、摘录 4.96:1**（要求 4.5:1），与写 CSS 前在 Python 里算的数字一致。
4. **标记不可能改变折行**：断言 `mark` 的 padding 与 border 八项全为 0。

**同时如实记下它做不到的事。** 标记只认字面查询词。服务端在字面命中过少时会用策展近义词补召回
（`SYNONYM_GROUPS`，例如 `('报名','申请','申报')`），这类命中在界面上**没有任何标记**，
读者看不到它为什么被列出。实测例：查询「奖学金申请材料」返回 2 条，第 2 条「【演示】校园竞赛报名」
是由近义词「报名」命中的。排序本身已经把字面命中排在近义词命中之前（有既有用例钉住），
所以不会顶掉字面结果；但要显示「为什么是这条」，需要接口返回命中词，而公共契约冻结在 1.5.0——
本轮**没有**为了这一个显示效果去改契约，而是把限制写进了 [ACCEPTANCE.md](ACCEPTANCE.md) 和 [源码导航.md](源码导航.md)。

## 仍然保持的边界

- 8 个跳过用例仍是依赖独立 PostgreSQL 的并发/租约测试，本机没有 PostgreSQL，**不是通过项**；`deploy/cloudrun/test_postgres_local.py` 需要单独核验的 PostgreSQL bin 目录。
- 并发首次启动的修复只覆盖 **SQLite 全新数据库**；PostgreSQL 上的并发建表与租约仍未执行（即那 8 个跳过用例）。
- 近义词命中在界面上不显示标记（见上），要消除它需要改动已冻结的公共契约。
- 本轮浏览器验收**未运行中文 OCR 模型**（需 `CAMPUS_E2E_OCR=true` 与 Tesseract 模型下载），报告内如实标注 `not run`。
- 真实校园网络、公众号授权、生产 SMTP、个人网关实际送达、Google Cloud 部署与真实学生试用仍需目标环境验收。

数据库一致性、清理范围、发行文件清单、包哈希、测试结果和跳过项**以最终验收报告为准**，见 [ACCEPTANCE.md](ACCEPTANCE.md)。本文件不把历史报告的通过数量或跳过结果算成本轮验收。
